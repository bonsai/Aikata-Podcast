# POC — Proof of Concept

## 目的
本実装前に、成立を左右する技術リスクと制作体験の仮説を小さく検証する。POCは完成品ではなく、結果を記録して設計判断に使う。

## 検証項目

| ID | 仮説 | 実験 | 合格条件 |
|---|---|---|---|
| POC-01 | ブラウザ録音を保存・再生できる | MediaRecorderで短い音声を録音 | 録音・再生・やり直しができる |
| POC-02 | 日本語TTSが使える | 候補サービスで短い台詞を生成 | 音声、品質、遅延、料金、利用条件を記録 |
| POC-03 | 人間音声とTTSを合わせられる | 2つの音声を順番に再生・ミックス | 音声出力が再生でき、順序と音量を制御 |
| POC-04 | Cloudflareで保存・取得・削除できる | Workers、D1、R2の小規模実験 | 認可付きCRUDと制限・費用を確認 |
| POC-05 | 3分制作フローが理解しやすい | 3〜5名に簡易UIを試してもらう | 詰まりと改善点を観察記録に残す |
| POC-06 | 1本あたりの原価が許容範囲 | LLM/TTS/保存/出力コストを計測 | 実測原価を算出し価格仮説と比較 |

## 推奨順序
1. 録音・再生の縦切り
2. 日本語TTS候補の品質・商用条件・遅延・コスト比較
3. ミックス・書き出し方式と形式互換性
4. D1/R2保存、認可、削除、サイズ制限
5. 初見ユーザーによる操作テスト
6. 実際のエピソードで変動費計測

## 実験記録テンプレート
- ID / 日付 / 実施者
- 仮説、環境、ブラウザ、モデル、プロバイダー
- 入力条件、再現手順、期待結果、実際の結果
- 所要時間、エラー、コスト、制限
- 合格 / 不合格 / 保留
- 証拠（ログ、画像、短いテスト音声、コミット）
- 設計への影響、次の判断

## 必ず確認するリスク
日本語TTSの自然さ・商用条件、生成遅延と失敗率、ブラウザごとのコーデック、ミックスとMP3/WAV出力、大きなファイルの転送制限、R2認可と削除整合、第三者音源・声の権利、1本あたりの変動費。

## 判断ルール
- 合格条件を満たす前に技術選定を確定しない。
- 不合格ならプロバイダー変更、ブラウザ内処理、MVP縮小を比較する。
- 実験結果がない項目を検証済みとしない。
- 結果はCONTEXTまたはADR相当の記録へ反映し、PRD/MVPも同期する。
